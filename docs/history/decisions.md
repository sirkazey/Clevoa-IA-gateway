# Décisions

Décisions de conception et leurs raisons, datées. Document d'archive : une décision n'est modifiée que par une
nouvelle entrée qui la remplace. Les audits qui les ont motivées : [audits d'octobre 2026](audit-2026-10.md).

| Date | Décision | Raison | Conséquence |
|---|---|---|---|
| 2026-10-21 | Un seul conteneur, connecteurs en modules, pas de framework ni de base de données | la solution doit rester une petite machine lisible en une heure | 3 dépendances, ~1 060 lignes, un fichier d'état chiffré |
| 2026-10-21 | Aucun compte de service ; jeton personnel transmis tel quel | les droits de chaque système s'appliquent sans réimplémentation | sans connexion du collaborateur, aucun outil ne répond |
| 2026-10-21 | Clé MCP uniquement en en-tête `Authorization`, jamais dans l'URL | une clé dans l'URL finirait dans les journaux des reverse proxys | claude.ai web et mobile non pris en charge |
| 2026-10-21 | Pas de serveur OAuth 2.1 côté hub | le hub reste sur le réseau interne ; les assistants installés sur les postes couvrent le besoin | claude.ai web et mobile écartés définitivement |
| 2026-10-22 | `users.json` chiffré AES-256-GCM avec clé maîtresse par environnement, sans rotation de clé | 24 lignes, zéro dépendance ; changer de clé = tout le monde se reconnecte | clé au coffre, jamais avec les sauvegardes |
| 2026-10-22 | Transport SSE conservé à côté du Streamable HTTP | compatibilité des assistants ; `/messages` exige la clé qui a ouvert la session | à retirer en premier quand les assistants seront tous en Streamable HTTP |
| 2026-10-23 | Salesforce par le serveur MCP hébergé SObject Reads, pas par l'API REST | lecture seule garantie par Salesforce ; outils et droits natifs | une session MCP par appel ; crédits Flex ; `SF_MAX_PER_MIN` |
| 2026-10-23 | Pas de factorisation entre connecteurs proxy (Salesforce, Dropbox, MyReport) | gain nul, abstraction en plus | à revoir seulement si un quatrième proxy arrive |
| 2026-10-23 | En production, un connecteur sans configuration n'est pas exposé | aucune donnée inventée possible en production | simulateurs réservés à la pré-production |
| 2026-10-23 | `SF_MCP_URL` acceptée seulement si elle désigne `…/sobject-reads` (liste blanche) | une liste noire des serveurs d'écriture aurait laissé passer un nouveau serveur | |
| 2026-10-24 | SSO Entra ID implémenté dans le routeur OAuth existant, sans oauth2-proxy ni composant supplémentaire | ~75 lignes, mêmes flux (code + PKCE), un seul conteneur | SSO = authentification seulement, jamais d'autorisation Graph |
| 2026-10-24 | Clé toujours fraîche à la première liaison SSO ; clé antérieure au SSO jamais reprise | revue indépendante : fixation de session, jetons d'un autre collaborateur | activer le SSO invalide les clés existantes |
| 2026-10-24 | Conteneur de sauvegarde avec la seule capacité `DAC_OVERRIDE` | lire le volume en 700 et écrire dans `BACKUP_DIR` quel qu'en soit le propriétaire ; un `chown` par l'administrateur est fragile sous Portainer | documenté dans l'exploitation |
| 2026-10-24 | Mode démo du portail retiré | quatrième couche de simulation, sans test, périmée ; le bouchon joue ce rôle | |
| 2026-10-24 | nginx fourni en profil Compose `proxy`, optionnel | https obligatoire en production sans imposer un reverse proxy | une seule stack par machine peut porter le profil |
| 2026-10-24 | Campagne de charge sur bouchons avant toute mesure sur les systèmes réels | mesurer d'abord, corriger ensuite ; ne jamais charger un système réel | corrections proposées séparément, aucune appliquée en 1.2.1 |
| 2026-10-24 | Produit nommé Clevoa AI Gateway, édité par Clevoa SASU ; Charlois = client et contexte de déploiement | identité produit et licence propriétaire | identifiants techniques inchangés dans la 1.2.1 pour éviter toute régression |
| 2026-10-25 | Reprendre un composant éprouvé plutôt qu'écrire du code maison pour tout ce qui n'est pas propre au produit : openid-client pour le SSO et SharePoint, express-rate-limit pour toutes les limites de débit | la vérification maison de l'id_token ne contrôlait pas la signature ; deux limiteurs coexistaient | 5 dépendances directes ; signature des id_token vérifiée ; [registre](../developer/dependances.md) |
| 2026-10-25 | Dépendances suivies en continu : SBOM CycloneDX et contrôle des licences en CI, Dependabot hebdomadaire vers `dev` avec 7 jours de délai | savoir ce qui tourne chez le client et être prévenu d'une faille ou d'une version | une PR Dependabot par semaine et par écosystème à relire |
| 2026-10-24 | 1.3.0 : nom du serveur MCP et libellé d'instance paramétrables (`MCP_SERVER_NAME`, `INSTANCE_LABEL`), bouchon renommé `clevoa-mcp-stub`, paquets `clevoa-gateway-hub` et `clevoa-mcp-stub` | socle multi-client sans valeur Charlois codée en dur ; le nom du serveur n'est qu'une clé locale chez le client MCP, le changer ne casse aucune configuration | jeu de données fictif du bouchon conservé (e-mails `@charlois.com`, tables YFAC/ZVENTE) : cohérent avec les tests, à neutraliser seulement pour un second client |
| 2026-10-24 | Gel du périmètre fonctionnel à la 1.3.1 ; seule roadmap active : [roadmap produit](../roadmap-produit.md) (qualification, maintenance, intégrations sur besoin) | aucune instance cliente déployée ; la valeur dépend désormais de la qualification réelle, pas de nouvelles fonctions | évolutions limitées aux corrections, à la sécurité, à la compatibilité MCP et API, à l'exploitation et aux connecteurs demandés par un client |
| 2026-10-24 | Chantier de registre d'Agent Skills abandonné ; branche `docs/roadmap-skills-adoption-2026-10` conservée comme archive, non fusionnée | le produit ne devient ni registre, ni outil de création de Skills, ni chatbot, ni plateforme de gouvernance IA ; la création de Skills relève du conseil Clevoa et des assistants | aucune référence active aux Skills dans la documentation |
| 2026-10-24 | Maintenance par versions correctives, sans prise de contrôle à distance ; diagnostic exporté et relu par l'administrateur ; télémétrie éditeur persistée dans le backend Clevoa existant | Clevoa doit savoir quelles versions tournent sans accéder à l'infrastructure ni aux données du client | pas de tunnel, d'agent distant ni de mise à jour automatique imposée |
| 2026-10-24 | Multi-client : un seul code, une installation par client, déployée depuis un tag Git jamais déplacé (convention, protection des tags à poser) ; configuration et secrets dans la stack du client ; aucune branche permanente ni fork par client | une installation ne doit pas changer au gré des commits de `main` ; une personnalisation passe par la configuration | `main` et `dev` restent des branches d'intégration ; la production d'un client référence `refs/tags/vX.Y.Z` |
| 2026-10-25 | Suivi des installations par Clevoa : télémétrie toutes les 6 h avec statistiques par connecteur (appels, erreurs par type, collaborateurs distincts, latences) ; e-mail seulement à l'ouverture et à la fermeture d'un incident (erreurs du système, authentification refusée pour tous, silence de 14 h) ; console de suivi en lecture seule, en conteneur sur un NAS du réseau privé de Clevoa | demande de la direction de Clevoa : les données stockées doivent servir au suivi de la qualité de service, et les alertes ne doivent signaler que les erreurs chez le client ; système non critique pour l'entreprise | remplace, pour le seul « tableau de bord graphique des installations », le classement hors roadmap du 2026-10-24 ; la console n'agit sur aucune installation, n'est jamais exposée sur internet, et ne lit la table qu'avec une politique IAM de lecture ; plus d'e-mail pour une version ancienne |
| 2026-10-25 | Portail 1.4.0 pensé comme un outil de connexion et non comme une page d'accueil : une ligne par application classée par domaine, assistant à brancher sans défilement, questions par domaine ; état de chaque système (appels réels de la dernière heure et requête HEAD sans identifiant toutes les 10 minutes, du lundi au vendredi de 7 h à 19 h) ; supervision du hub par `/metrics` au format Prometheus, jeton dédié | demande de la direction de Clevoa : la page « ne marche pas » (titre et cartes trop grands, trois écrans à parcourir) ; un collaborateur doit voir qu'une panne n'est pas celle de son compte ; l'administrateur du client doit pouvoir superviser le hub | remplace, pour la seule « santé des connecteurs sur le portail », le classement hors roadmap du 2026-10-24 et lève le gel du périmètre pour cette version ; toujours aucun compte de service (la vérification ne prouve que la joignabilité) ; SNMP écarté (communauté en clair en v2c, agent et MIB à maintenir) au profit d'un format lu par la plupart des outils ; groupe de domaine vide jamais affiché |
| 2026-10-25 | Node 24 et base d'exploitation SQLite intégrée (`node:sqlite`, `/data/hub.db`) pour l'historique de disponibilité, les compteurs d'usage et le journal d'audit ; `users.json` reste inchangé et seule source des identités et des jetons | réécrire un fichier JSON entier à chaque compteur multiplie les risques ; SQLite écrit une ligne à la fois (WAL), sans dépendance ni service, et ouvre l'historique et la mesure de l'usage | remplace, pour ces seules données, le « pas de base de données » du 2026-10-21 (toujours pas de serveur de base) ; une base inutilisable n'arrête jamais les outils ; un retour à la 1.4 ignore `hub.db` ; instantané horaire sauvegardé par `mcp-backup` |
| 2026-10-25 | Journal d'audit désactivé par défaut (`AUDIT=on`), sans arguments ni données renvoyées, e-mail chiffré, export par l'administrateur seulement (`docker exec`) ; collaborateurs comptés par pseudonyme HMAC | l'audit est un traitement de données personnelles du client : finalité, information des collaborateurs et durée relèvent de son DPO | aucune route HTTP vers ces données ; rien n'en part dans la télémétrie ; conditions d'activation dans [sécurité § 7](../admin/securite.md#7-base-dexploitation-et-journal-daudit-15) |
| 2026-10-26 | Résolution des noms du hub en IPv4 d'abord, puis IPv6 (`hub/resolve.js`, enveloppe de `dns.lookup`), plutôt qu'une image Debian ou une adresse IP figée | constaté au premier test SharePoint réel : sous Docker Desktop, musl (image Alpine) ne rendait que l'IPv6 de `login.microsoftonline.com` ; changer d'image en version candidate déplace tout le reste (taille, analyses, retour arrière), une adresse figée casse au premier changement chez Microsoft | aucune dépendance ; un hôte IPv6 seul reste joignable ; une famille imposée par l'appelant est respectée |
